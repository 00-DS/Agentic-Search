## 1. 背景与问题

FastAPI 在启动 uvicorn 后自动提供**两个** API 文档界面，零额外代码：

| URL | 性质 | 长什么样 |
|---|---|---|
| `/redoc` | **文档视图（只读）** | 三栏布局：左侧端点目录、中间参数/响应结构详情、右侧示例。排版漂亮，适合通读全貌，但**发不了请求**。 |
| `/docs` | **交互视图（Swagger UI）** | 每个端点能展开 → 点 **Try it out** → 填参数 → **Execute** → 看真实返回（JSON / SSE）。适合实际试一遍。 |

二者背后共用同一份 `/openapi.json`（机器可读的 OpenAPI 规范），由 FastAPI 从**类型标注 + Pydantic 模型**自动生成。改代码 → 规范更新 → 两个界面同步更新。

**当前 gap**：doc 02 在 L492（schemas 说明段）、L802（验证标准）、L880（完成检查）三次**提到** `/docs`，但从未**教**学生它是什么、怎么用、两个 URL 的分工。学生被告知「访问 /docs」却不知道这是干什么的。

**教学动机**：当前验证链是「第 10 步启动服务 → 第 11 步写 pytest」。中间缺一个「手动直观感受」环节。新增独立步骤后脉络变成：**启动 → 手动直观感受 → 写自动化测试**，符合「先亲眼看到再抽象成测试」的学习顺序。

## 2. 关键技术事实（均已运行时验证）

- 两个 URL 都活着（TestClient 验证）：`GET /docs` → 200 `text/html`；`GET /redoc` → 200 `text/html`；`GET /openapi.json` → 200 `application/json`。
- `/api/query` 在 OpenAPI 规范里被正确文档化为 SSE 端点：`responses.200.content` 含 `text/event-stream`，`itemSchema` 描述了 `ServerSentEvent` 的 `data`/`event`/`id`/`retry` 字段。所以 `/docs` 能对 query 端点点 Try it out。
- **Swagger UI 对 SSE 的行为局限**（关键教学点）：Swagger UI 会等 agent **完整跑完**后一次性显示全部 SSE 帧文本，**不是逐字流式出现**。即学生会在 Execute 后等几秒，然后看到一长串 `data: "..."` 行——这是 wire 格式全文，不是流式动画。逐字流式效果要用第 10 步 `httpx.stream` 或模块 3 前端。
- **不改代码**：两个 URL 是 FastAPI 默认行为，`main.py` 的 `FastAPI(title=...)` 自动挂载，无需任何新增。

## 3. 决策：方案 A（独立教学步骤，4 个端点全试 + 双 URL 对比）

### 3.1 方案对比

- **方案 A（选定）**：新增独立「第 11 步」，介绍两个 URL 的分工，在 `/docs` 里逐个试 4 个端点（含 SSE 端点 + 诚实说明 Swagger 的流式局限），呼应 schemas.py。
- **方案 B（弃）**：只在第 10 步验证段插一段「打开 /docs 试试」。更轻，但把「教工具」混进「验证命令」，且只覆盖 `/docs` 一个 URL（用户明确要两个都要）。

### 3.2 选 A 的理由

1. **用户明确要独立教学步骤**（放在 pytest 之前，作为「手动直观感受」环节），不要混进验证段。
2. **用户明确要两个 URL**（一个文档、一个动态）。方案 A 的 ① 段专门对比 `/redoc`（只读文档）vs `/docs`（交互动态）的分工，B 只提一个。
3. **教学完整**：学生在一个步骤里既看全貌（redoc）又亲手试一遍（docs 的 Try it out），再把端点结构与第 7 步 schemas.py 呼应，形成闭环。
4. **契合现有模块节奏**：doc 02 的每一步都是独立主题（包化、ReAct、装饰器、配置……），新增「Swagger UI」作为独立步骤与现有风格一致。

## 4. 改动清单

### 4.1 新增「第 11 步」（插入 L804 之后、当前 L806 之前）

标题：`## 第 11 步：用 FastAPI 自带文档界面直观感受你的 API`

内容分 5 段：

**① FastAPI 自带的两个 API 文档界面**

> 启动 uvicorn 后，FastAPI 零额外代码给你**两个**自动生成的 API 文档界面，都从你的类型标注 + Pydantic 模型生成（背后是 `/openapi.json` 这份机器可读的 OpenAPI 规范）。二者用途不同：
>
> - **`http://localhost:8000/redoc`** —— **文档视图**（只读）。三栏布局：左侧端点目录、中间参数/响应结构详情、右侧示例。适合**通读全部 API 长什么样**，但发不了请求。
> - **`http://localhost:8000/docs`** —— **交互视图**（Swagger UI）。每个端点能展开 → 点 **Try it out** → 填参数 → **Execute** → 看真实返回的 JSON / SSE。适合**实际试一遍**。
>
> 日常调试用 `/docs`（能试）；想看全貌或分享给别人读用 `/redoc`（排版漂亮）。两个都基于同一份 OpenAPI 规范，改了代码两个同步更新。

**② 在 /docs 里逐个试你的 4 个端点**

> 打开 `http://localhost:8000/docs`，点开每个端点 → **Try it out** → 填参数 → **Execute**：
>
> - **GET /api/documents** —— 返回 JSON 文档列表（第一次为空数组 `[]`，上传后能看到条目）。
> - **POST /api/ingest** —— 上传一个 PDF 文件 → 返回 `{"doc_id": "...", "filename": "..."}`。
> - **POST /api/consolidate** —— 填 `session_id` → 返回 `{"status": "pending", "l2_id": ""}`（模块 4 才接入真实逻辑）。
> - **POST /api/query** —— 填问题（如「你好」）→ **等几秒**（agent 在跑）→ 返回一整段 SSE 文本。

**③ /api/query 在 Swagger 里的样子（一个要注意的局限）**

> `/api/query` 的 Execute 会等 agent 完整跑完后，一次性把全部 SSE 帧文本显示出来——你会看到一长串 `data: "\u4f60\u597d"` 这样的行，这就是 SSE 流的 wire 格式（第 8 步讲过）。
>
> 注意：**Swagger 等整段跑完才显示，不是逐字流式出现**。要感受「逐字打字」的流式效果，用第 10 步的 `httpx.stream` 命令、或模块 3 的前端界面。Swagger 在这里的价值是**验证端点能跑 + 直观看到 wire 格式全文**，不是看流式动画。

**④ 为什么 Pydantic 模型这么重要——第二个回报**

> 注意面板里每个端点的请求/响应结构——`QueryRequest` 的 `question` 字段、`IngestResponse` 的 `doc_id`/`filename`——这些全来自第 7 步 `schemas.py` 里的 Pydantic 模型。这就是「认真定义模型」的第二个回报：除了第 7 步讲过的自动校验（缺字段返回 422），还自动变成了这个**人能读的交互文档**。改模型，面板同步更新。

**⑤ 小结**

> 现在你已经亲手试过每个端点、确认它们能正常工作。下一步（第 12 步）把这些验证**固化成 pytest 自动化测试**——把「手动点一下看看」升级成「每次改代码自动跑一遍」。
